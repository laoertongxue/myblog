</details><h2 id="模块-sg04-cod订单风险与有限人审状态机">模块 SG04
COD订单风险与有限人审状态机</h2>
<p>对应D01、D02。目标是预测拒收风险并展示一条不会绕过人审的离线流程。风险高不等于欺诈，不等于应取消。历史地区差异也不是对某类人的价值判断。</p>
<h3 id="第一步-把实时要求拆成可检查的输入契约">第一步
把实时要求拆成可检查的输入契约</h3>
<p>COD是货到付款。模型使用address_complete地址是否完整、night_2_5下单是否在2至5时、pieces件数、basket100客单百元、history_sign_rate历史签收率、prior_orders既往次数、remote_region模拟偏远区域0/1。实际地址、手机号不进入本项目，所有实体匿名虚构。</p>
<p>历史率用平滑：(历史签收数+1)÷(历史单数+2)。新顾客历史0单得到1÷2=0.5，不能误写成0%签收。历史8单签收6单，则(6+1)÷(8+2)=0.7。它只是本教学基线，不代表正确的全公司先验。历史记录必须在评分时已知，history_known_at&gt;score_time时函数直接拒绝。</p>
<p>score_cod(model,features,score_time,history_known_at,calibration_offset)是本地函数，检查缺字段、非有限特征、非有限时点和未来历史，再加上同一个已冻结校准偏移返回概率。批量评分与这一路径必须一致，不能在线返回原始概率却用校准后阈值。一次本地函数耗时不等于网络服务SLA：没有API网关、消息总线、鉴权、重试、并发、特征存储或线上可用性验证。教程把“实时评分需要什么输入”做成可运行契约，没有假装部署实时服务。</p>
<h3 id="第二步-训练-校准-选阈值用四块时间">第二步 训练 校准
选阈值用四块时间</h3>
<p>实际训练逻辑回归，2000单训练；400单校准；400单选择阈值；800单测试。训练日0至99，最晚109日标签成熟；校准120至139，最晚149日成熟；选阈值160至179，最晚189日成熟；测试200至239，最晚249日成熟。每一步的标签全部可用后，才进入下一块的评分时点。cod_fit_timeline.csv列出这条时间线；旧的“校准到139日却从140日选阈值”会被拒绝，因为139日订单要到149日才有标签。label_known_at被改为999也必须拒绝，不能只检查历史特征。</p>
<p>逻辑回归分数与第一章同形式，最终用sigmoid压到0至1。校准阶段只调整一个截距：原分数z，加校准偏移δ，得到p=1÷[1+exp(−z−δ)]。δ来自校准块，不能用最终测试答案。默认δ约0.05，不是把概率统一加5个百分点。</p>
<p>本次测试Brier约0.12875，均值基线约0.14037。它证明本合成数据里排序/概率预测有一些价值，不能证明人工复核会减少拒收。</p>
<h3 id="第三步-阈值必须同时考虑容量">第三步 阈值必须同时考虑容量</h3>
<p>玩具假设拒收损失100元，每次复核5元，复核能把拒收概率相对降低30%。这一“30%”是显式假设，不是实验估出的处理效应。对风险p的一单，不复核期望损失100p；复核期望损失5+100p×(1−0.3)。当复核更划算：</p>
<p>5+70p&lt;100p → 5&lt;30p → p&gt;1÷6≈0.1667。</p>
<p>但每日只能复核3单，不能给全体p&gt;0.1667的人都派工。程序在验证块比较0.2至0.8的七个阈值；超过阈值后，每天只取风险最高的3单。默认阈值0.2，测试中210单被标高风险，只有116单被容量选中，二者不能混报。</p>
<p>白皮书举p&gt;0.6是业务规则例子，不是普适最优阈值。项目CSV包含0.6候选，可直接比较规模。即使本例0.2成本较低，只要30%改善假设不成立，推荐也可能反过来。可把改善率做0%、10%、30%、50%敏感性表，但不得称为真实A/B收益。</p>
<h3 id="第四步-状态机让每一步有出处">第四步 状态机让每一步有出处</h3>
<p>状态机就是“现在在哪一格，收到什么事件，允许走到哪一格”。离线样例定义如下：</p>
<ul>
<li>SCORED评分结束：低风险进入RELEASED放行候选；高风险进入HOLD挂起候选。</li>
<li>HOLD有复核容量进入REVIEWING；没有容量进入REVIEW_QUEUED排队。</li>
<li>REVIEWING收到顾客确认进入CONFIRMED；还需带审核员编号的reviewer_approved，才到RELEASED。</li>
<li>REVIEWING收到顾客否认进入CANCEL_RECOMMENDATION取消建议，不执行真实取消。</li>
<li>HOLD、REVIEWING、REVIEW_QUEUED超时统一进入EXPIRED_REVIEW待补审，不自动放行。</li>
<li>EXPIRED_REVIEW只有带审核员编号的批准才进入RELEASED；没有编号就拒绝。</li>
</ul>
<p>五个固定案例A至E分别展示确认放行、否认建议、排队超时、低风险、超时后人工批准。cod_state_machine_trace.csv记录前状态、事件、审核员、后状态。重复给已经RELEASED的订单发批准事件会拒绝，避免重复动作被误当成合法下一步。这里没有真正的工单ID分配、持久化锁或跨系统幂等保证，不能把这个纯函数说成生产工单平台。</p>
<p>“顾客确认了”不是“之后签收了”。人审反馈只能更新流程状态；拒收模型标签仍要等真正配送结果成熟。如果把“审核员放行”当签收标签，模型将学习历史审核员的选择，而不是用户实际签收。</p>
<h3 id="第五步-如何验证而不夸大因果">第五步 如何验证而不夸大因果</h3>
<p>结构验收：未来历史和缺字段必须拒绝；一天最多3单；超时绝不能直接RELEASED；无审核员不能批准；用户否认只能产生取消建议；重复非法转移要报错。53项测试中的这些检验能说明代码遵守了样例规则，不能说明人审有效。</p>
<p>若将来要估计人审因果效果，需要额外批准后的随机试验：在预先确定且容量容许的同类合格订单中随机分配“邀请复核”或常规处理，事先固定主要指标为成熟后的拒收/成本，记录分组、邀请、回应、实际处理和完整随访；按最初分组做意向治疗比较。不能只比较“接受复核的人”与“没回应的人”，因为两群可能本来就不同。需防止重复顾客跨组污染，并制定超时与服务安全规则。本项目只交付试验设计，没有执行试验、联系用户或声称识别处理效果。</p>
