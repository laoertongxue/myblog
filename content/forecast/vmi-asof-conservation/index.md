<h3 id="先逐日算厂内-再算全网">4.3 先逐日算厂内 再算全网</h3>
<p>M1第1日领10，厂内可用12−10=2；待检仍2。第2日先收旧在途8与新补8，可用变18，再领14，余4。两日领用24，目标缓冲4保住。</p>
<p>M2第1日9−6=3；第2日3+10−10=3。两日领用16，缓冲3保住。</p>
<p><strong>厂内账：</strong>期初可用+实际收货−领用=期末可用。M1为12+8+8−24=4。注意新增订单8不是一下单就加入厂内库存，发运后也先进入在途。</p>
<p><strong>全网物理账：</strong>期初供应商+期初厂内可用+期初待检+期初在途=期末所有位置+累计消耗。</p>
<p>M1初始总数40+12+2+8=62。发8之后供应商32；两日后厂内可用4、待检2、在途0。62=32+4+2+24=62。</p>
<p>M2初始39，期末供应商20、厂内可用3，累计消耗16；39=20+3+16。</p>
<p>调拨/收货只改变位置，不凭空创造数量。消耗才使本例全网物料存量减少。所有库存行保留owner来源标签；货在工厂不代表已经归工厂，也不能把同一批供应商库存和工厂寄售库存重复当两份供给。这里owner标识未消耗寄售物料的所有者及消耗来源，不是消耗时从供应商转给工厂的产权分录。本例只验物理数量，不声称已验证产权转移或责任余额守恒。</p>
<h3 id="晚到通知与实物延误是两层不同事实">4.4
晚到通知与实物延误是两层不同事实</h3>
<p>旧在途M1有两个通知版本：</p>
<ul>
<li>版本1在第1日07:00已知：8件第2日到。</li>
<li>版本2在第1日12:00才发布：改为第3日到。</li>
</ul>
<p>08:00决策不能用12:00版本。脚本先全局核验shipment_id/revision唯一，再按available_at选当时最新版本；过时重复版本也拒绝，与输入行顺序无关。两个实际到货情景共享同一份08:00计划，防止用未来延误真值帮模型作弊。</p>
<p>实物回放另读vmi_initial_transit_scoring_only.csv作为初始在途快照，不从可见通知构造物理初态。如果两个通知都晚到09:00，08:00补货建议可能变12，但真实旧在途仍为8，全网期初仍62；按时回放旧到货仍入8。仅修改通知数量也不能改掉实际初态或实收量。通知账用于当时决策，独立实物账用于事后评价，二者不相互冒充。</p>
<p>延误情景：第2日只有新增8到。M1第1日剩2，第2日2+8=10，需要14，缺4。此时已消耗20，厂内可用0、待检2、供应商32、旧在途8；62=20+0+2+32+8。延误不是库存消失，也不能把还在途的8变成可领用。</p>
<p>若在第1日13:00重新决策且当天尚未进行本例的日末领用，已经能看见第3日到达通知。覆盖期内旧在途不计，IP变12，原始缺口16；供应商最多发12，建议受限为12，仍有目标差4。第2日2+12−14=0，需求能满足但缓冲没有保住。这说明“目标库存没达成”与“本期已经缺货”不是一回事。</p>
<p>本例只模拟两日与既定新增交期，不建立运输中断概率、财务结算或复杂冻结区。旧在途实际到货文件名称含scoring_only，它用于事后回放，不进入08:00建议的输入。</p>
<h3 id="协同流程与小项目">4.5 协同流程与小项目</h3>
<p>需求版本冻结 → 供应商建议草稿 → 工厂核对需求/库容/权限 → 模拟批准 →
发运减供应商加在途 → 收货减在途加厂内 → 领用减厂内 → 对账。</p>
<p>本包的“批准”只表示离线回放采取该方案，不是现实授权。真实系统需要审核状态、不可重复的建议/事件ID、接收回执和失败恢复。脚本拒绝重复通知版本/需求行，逐事件校验非负库存、库容和总量守恒，未实现外部ERP接口。</p>
